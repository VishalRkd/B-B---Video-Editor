# 1. Executive Finding

Audit complete for the current source at `0411e250834307ee4b2528db016be2a2e1f600d5` (2026-10-30). Investigation only; no production/test/dependency changes or new decode experiments.

The displayed text is generated by the app's **preview admission policy**, not by a failed MediaCodec initialization. `PreviewResourcePolicy.assess()` finds no regular non-encoder codec satisfying its MIME + encoded-size + source-FPS predicate, records the message and returns `UNSUPPORTED`. `PreviewEngine.compileProject()` throws on that decision **before** `optimizer.resolve()` or new preview-player preparation. The predicate/branch order is proven; the failing phone's codec names, source FPS/profile/bit depth, individual false results/exceptions and actual decoding ability are **unknown**. The message does not preserve that evidence. Generating a proxy would still require decoding the original; routing correction alone cannot guarantee success on genuinely unsupported hardware.

# 10. Current Admission Decision Tree

Model: **EngineResourceBudget.kt:31–35**, enum `ORIGINAL`, `REDUCED_OUTPUT`, `OPTIMIZED_MEDIA_REQUIRED`, `UNSUPPORTED`; only first two make `.admitted == true`.

```text
referenced visual VIDEO sources → enumerate/query every distinct media ID
  visual track count > maximumVideoInputs? → UNSUPPORTED (layer-limit reason)
  any source-query problem?                → UNSUPPORTED (the displayed message)
  HDR(transfer 6/7), declared > max,
    sourceBytes > budget, or knownFailure? → OPTIMIZED_MEDIA_REQUIRED
  sourceBytes + output texture cost > budget? → REDUCED_OUTPUT / FAST
  otherwise                               → ORIGINAL / requested quality
```

`declared > max` alone is unreachable after the first gate because declared video-containing tracks cannot exceed all visual tracks. `peakActiveVideos` is computed and returned, but **not used as a branch condition**. This distinction matters for a later resource-policy correction; it is not the cause of this exact format message.

# 13. Proxy Bootstrap Limitation

**OptimizedPreviewMedia.kt:59–68 → Media3RenderEngine.kt:34,47–68 → default Transformer asset loader → DefaultDecoderFactory → DefaultCodec** must read/decode the original 4K HEVC stream before emitting 720p AVC. There is **no recursive app admission-policy check** in normalization, so its rejection would not be the same policy message. It uses the same Android codec inventory underneath, a different Media3 decode route, default decoder fallback false, and no independent decoder backend.

Therefore a false-negative app size/rate query could coexist with successful normalization/export, but a genuinely undecodable HEVC profile/size cannot be made decodable merely by requesting a smaller output. Existing cached compatible media could avoid re-decoding, yet current original-first admission also blocks consulting that cache. Only actual device evidence can establish which route would work for this file.

# 14. Sequential Clips vs Simultaneous Decoder Accounting

**WorkspaceViewModel.kt:113–126** appends VIDEO imports to `track.durationUs`, iterates `nextStart=clip.endUs` and adds them to one compatible track. It does not create one video track per imported clip.

**EngineResourceBudget.kt:47–70**, current accounting:

```kotlin
val declared=plan.visuals.count{track->track.track.clips.any{plan.project.media[it.mediaId]?.kind==MediaKind.VIDEO}}
val sourceBytes=plan.visuals.sumOf{track->track.track.clips.mapNotNull{plan.project.media[it.mediaId]}
    .maxOfOrNull{it.width.toLong()*it.height*(if(it.kind==MediaKind.VIDEO)16 else 8)} ?: 0L}
val working=sourceBytes+width.toLong()*height*4*(plan.visuals.size+3)
```

Peak uses VIDEO clip start +1 / end -1 events, sorted by time then delta (ends before starts), so adjacent clips do not overlap. `RenderPlan.visuals` (**C/RenderPlan.kt:97–105**) means nonempty VIDEO/OVERLAY tracks, excluding text/audio. Each track's **maximum** source charge is summed; clip count is not multiplied by a decoder charge. Codec-query validation nevertheless scans every referenced video.

| Scenario | Logical peak / declared video tracks / policy implications |
| --- | --- |
| 10+ sequential videos, one VIDEO track | Peak 1, declared 1, visual tracks 1; max source size charge, not sum of all ten |
| Base + overlapping video overlay | Peak 2, declared 2, two source charges |
| Nonoverlapping videos on different visual tracks | Peak can be 1, but declared/visual track counts and charges remain larger; conservative static graph policy |
| Several simultaneous video overlays | Peak grows with actual overlapping video intervals; hard gate still uses total visual tracks |
| Gaps | No active video event within gap; declared track/maximum source charge remains |
| Image-only visual tracks | No VIDEO peak/declared count; still consume graph-input cap and width×height×8 estimate |
| Text-only layers | Excluded from these VIDEO counts/visual tracks; compiler handles captions/clock separately |

The layer cap is 2 on low-RAM/32-bit devices, otherwise 4; decoder working budget is heap/2 clamped to 48–256 MiB (**inspect():20–27**). No actual `maxSupportedInstances` result is used. One 3840×2160 video source charge is 132710400 bytes before output buffers. Peak logical activity is not proof of exact physical decoder count because Media3 may retain/prewarm resources.

**10+ is not a threshold in this failure.** More imports increase the chance that one globally validated source fails, even if that clip is not currently active. Ten separate visual tracks can cause a different layer-limit error. The static-track-versus-peak distinction deserves separate testing, not attribution as the cause of this message.

# 15. HEVC / 4K / Profile / HDR Handling

There is no preview branch hard-coded to reject `video/hevc`, 3840 or 2160. MIME and size/rate checks are generic. **A/export/ExportModels.kt:12,22,84–95** exposes AVC/HEVC output choices and encoder capability combinations including 2160; this is export encoding support, not HEVC input decoding proof.

Importer/policy cannot distinguish HEVC Main 8-bit from Main10 or levels. It can see declared frameRate (including 30 vs 60 when known) and transfer 6/7 to request optimization, but cannot validate HDR10/HLG decode requirements, standard/range, bit depth or dynamic/static metadata comprehensively. Transfer=0 is unknown, not proof of SDR. Main10 can also be SDR. Normalization asks compiler GL HDR→SDR tone mapping (**CompositionCompiler.kt:166–167**), subject to actual codec/GL support and upstream device/API restrictions; it is not guaranteed by the policy.

**Rotation:** **C/Project.kt:51–52** swaps display dimensions for 90°/270°. Admission checks stored encoded width/height unchanged and does not try the swapped orientation or normalize alignment. Normalization uses derived display dimensions for canvas (**OptimizedPreviewMedia.kt:59–63**), while Media3 reads original rotation from the stream. This does not automatically explain the real failure, but dimension provenance/portrait/asymmetric capability cases lack validation. Source FPS may also differ from project 30 FPS; the error omits it.

# 16. Preview Output vs Source Decode Resolution

The app explicitly separates these costs: **EngineResourceBudget.kt:38–39,65–79**, **PreviewQuality.kt:5–14**, **CompositionCompiler.kt:212–215,242–244**. `Presentation.createForWidthAndHeight()` scales decoded content; it does not select a lower-resolution encoded stream. **PreviewEngine.kt:583–586** records native initialization failures, then fails; it does not automatically normalize/retry. **EngineResourceBudget.kt:41–44,83** records signatures for **all videos in project.media**, including unused ones, not just the failing source. Different codecs in the same container/size/FPS can collide. This can over-trigger later normalization but cannot rescue the early capability rejection because that branch has priority. `fail()` also preserves any old admission object via state.copy, so visible error lacks a reliable structured failed admission.

# 18. Retry Preview Behavior

**A/MainActivity.kt:183–187** displays the engine string verbatim:

```kotlin
Text(error, fontSize = 12.sp)
TextButton(onClick = { engine.updateProject(project); engine.resume() }) { Text("Retry preview") }
```

`updateProject():168` returns immediately if the project is unchanged. `resume():198–202` recompiles when player is absent/error exists; `compileProject()` increments generation, clears pending work and reruns admission. It does not choose a new quality/decoder, clear a policy verdict, request a probe, bypass the failed branch or explicitly invalidate a proxy. The source-format reason survives as `PreviewState.error` → mapped surface error → UI, not a friendly classified recovery action. Retry can recover transient access/resource failures, or reach optimization after a native initialization failure recorded in policy. For this unchanged reported-capability rejection it repeats the same gate unless source metadata/platform results change; it does not record a native failure or initiate another route.

# 19. Preview vs Export Behavior

**ExportCoordinator.start():57–72** validates document/effects and storage, then starts export. **Media3RenderEngine.renderOwned():31–68** calls compiler then Transformer; neither invokes `PreviewResourcePolicy.assess()` or substitutes preview proxies. Export UI capability filtering (**ExportModels.kt:80–99**) evaluates output **encoders**, not source decoders.

Thus **preview may reject while export could decode**, and normalization could fail while direct export with another format/output/GL path succeeds; neither is proven for this phone. Conversely truly unsupported original decoding can fail in all routes. Preview uses CompositionPlayer/sequence renderers with decoder fallback explicitly false; export/normalization use default Transformer decoding with fallback false. Both ultimately depend on Android codecs, but selection/processing paths differ. Output encoder fallback true and `onFallbackApplied` do not supply an alternate HEVC input decoder. `synchronizedFrames=false` for normalization disables the app packet pipeline, not original-source decoding.

# 21. Root Cause Chain

```text
Real imported HEVC source with persisted width=3840, height=2160
  ↓ MediaImporter stores codecMimeType and source frameRate (or 0), limited color metadata
RenderPlan includes this source anywhere on a visual track
  ↓ PreviewResourcePolicy queries REGULAR_CODECS, excluding encoders
No candidate satisfies MIME + nonnull VideoCapabilities + areSizeAndRateSupported
  (or relevant individual query throws → false)
  ↓ problems includes the exact app-authored source-format message
UNSUPPORTED wins before HDR/memory/known-failure optimization routing
  ↓ PreviewEngine require throws IllegalArgumentException
optimizer.resolve / substituted-source reassessment / new player prepare are skipped
  ↓ catch → fail(message) → PreviewState.error / FAILED → surface.error
PreviewCanvas Text(error) + Retry preview; unchanged retry repeats the same check
```

The cause of the phone's negative advertised predicate and actual decodability remain section-26 unknowns; the above app causal path is established without inventing a device failure log.

# 23. Current Architecture — Keep / Change

**Keep:** immutable original Project/media, RenderPlan, retained preview executor, bounded requests/queues, original audio/export URIs, source-time variants, cancellation/atomic promotion/leases and explicit resource limits.

**Strengthen:** source-aware compatibility evidence and diagnostics; distinguish reported NO/unknown from observed decode failure; bounded safe decoder verification/selection; route eligible sources to existing variants/normalization; verify variant codec/FPS/color rather than label them; typed failures and meaningful retry; isolate per-source decode needs from static graph-input limits. Preserve safety budgets and all layers.

**No evidence currently justifies a new decoding backend.** Existing Transformer decoder-factory injection plus current substitution/ownership architecture can support a substantial clean fix. It cannot promise that Android will decode every real HEVC source. An additional backend would need evidence that all appropriate exposed decoders/probe/normalization paths fail, plus a separately justified support/product decision. Enabling a public CompositionPlayer fallback option is not available in the pinned version (section 9).
